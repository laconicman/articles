## 1. Машиночитаемого документа нет

Справочник отрендерен **из** OpenAPI-документа: страницы вида
`/api/express/openapi/IntegrationV2ClaimsCreate` показывают схемы, типы, `Pattern`, `Enum`, коды ответов.
На странице нет ни одной ссылки, ведущей на `.json`/`.yaml`, нет слов «скачать» или «спецификация»
(проверено программно: выборка всех `<a href>` по маске `\.(json|ya?ml)|download|spec` — пусто).
Заголовка `Last-Modified` страницы не отдают (`cache-control: no-store`).

Следствие: сгенерировать клиент по-прежнему не из чего. Документ у вендора есть — наружу отдан рендер.

## 2. История изменений остановилась в 2023 году

`releases.md` — таблица из трёх строк, все три датированы **17.07.2023** (добавление
`offers/calculate`, параметр `offer_payload` в `claims/create`, `expected_visit_interval` в ответе
`claims/info`).

При этом в оглавлении (`llms.txt`) сегодня перечислены методы, которых в той таблице нет вовсе:
редактирование заявки до и после подтверждения (`IntegrationV2ClaimsEdit`, `ClaimsApplyChangesRequest`,
`ClaimsApplyChangesResult`), пропуск точки (`IntegrationV2ClaimsReturn`), поиск и журнал изменений,
код подтверждения, подтверждение доставки, готовность точки к выдаче и три метода обмена
**с роботом** (`IntegrationV1RobotHandoverInitialize/Info/Confirm`).

То есть API за три года заметно вырос, а журнал изменений об этом молчит. Узнать, когда что
изменилось, читателю неоткуда.

## 3. Опечатка `droppof_point` — в примерах запроса, а не только в ответе

Док, `IntegrationV2ClaimsCreate`, пример тела запроса (встречается в файле четырежды):

```json
"pickup_point": 1,
"dropoff_point": 2,
"droppof_point": 0,
```

Описание поля в схеме — целиком, дословно: **«deprecated, use dropoff_point»**. Ни даты, ни срока
удаления; сам флаг `deprecated` OpenAPI при этом не выставлен — это проза в `description`.
В примере два поля с одинаковым смыслом имеют **разные значения** (`2` и `0`).

Провод (2026-08-12): в ответе каждый товар несёт оба поля с одинаковым значением
(`"dropoff_point": 26389626087876, "droppof_point": 26389626087876`).

## 4. Два словаря кодов ошибок — и они противоречат друг другу внутри документации

`errors.md` — «Справочник ошибок» на **11 строк** для API из тридцати с лишним методов. В колонке
«Сообщение» вперемешку символьные коды и человеческие фразы:

| Код | Сообщение (дословно) |
|---|---|
| 401 | `unauthorized` |
| 500 | `Internal server error` |
| 409 | `inappropriate_status` |
| 400 | `Parse error` |
| 400 | `too_many_loaders` — «Максимальное количество грузчиков — 2.» |
| 400 | `delay_too_long` — «Максимальное количество дней для поля `due` — 3.» |

А на странице `IntegrationV2OfferCalculate` ответ **409** документирован закрытым перечислением из
**23** значений, среди которых `estimating.too_many_loaders`, `estimating.warning.too_heavy_item`,
`estimating.route_too_short`, `estimating.swapped_coordinates`.

Итого одна и та же ошибка «слишком много грузчиков» описана в справочнике как `too_many_loaders` / 400,
а на странице метода — как `estimating.too_many_loaders` / 409. Провод (2026-08-12) подтверждает
второй вариант: `409 {"code":"estimating.too_many_loaders","message":"В выбранном кузове не получится
заказать столько грузчиков"}`.

Провод же показывает и третий регистр — числовой код-строку с внутренностями парсера:

```json
{"code":"400","message":"Parse error at pos 763, path 'route_points': incorrect size, must be 2 (limit) <= 1 (value)"}
{"code":"400","message":"Value of query 'claim_id': incorrect size, must be 32 (limit) <= 3 (value)"}
```

см. пункт 2.

## 7. Время

Док объявляет `string<date-time>`. Примеры в самой документации приходят в двух видах:
`"2020-01-01T07:00:00+00:00"` и `"2023-07-17T08:02:26.607358+00:00"`.

Провод (2026-08-12, TD-16): один ответ `offers/calculate` — 21 отметка с шестизначной дробной частью
и 4 без неё, включая один интервал, у которого `from` с дробью, а `to` без:

```json
"pickup_interval": {
  "from": "2026-08-12T17:12:40.051944+00:00",
  "to":   "2026-08-12T18:15:00+00:00"
}
```

**Важная оговорка для честности текста:** обе формы валидны по RFC 3339 — дробная часть там
опциональна. Претензия не в нарушении стандарта, а в том, что формат меняется внутри одного объекта,
и потому читающая сторона обязана быть либеральной, а пишущая — угадывать.

## 8. Деньги

Док, `Pattern` для `total_price` и `total_price_with_vat`: `^-?[0-9]{1,14}(\.[0-9]{0,4})?$`.
Этот шаблон допускает четыре знака после запятой у денег и — из-за `{0,4}` — строку с точкой и
пустой дробной частью (`"1449."`).

Провод: `"total_price":"1449"` и `"total_price_with_vat":"1767.78"` в одном объекте.

## 9. Вебхук склеивает URL конкатенацией — и это задокументировано

Док, `claims/create`, описание `callback_properties`, дословно:

> Важно: параметры добавляются конкатенацией к callback_url, то есть url вида 'https://example.com'
> превратится в невалидный 'https://example.comupdated_ts=...&claim_id=...'.

То есть дефект описан вместо того, чтобы быть исправленным. Плюс `updated_ts` и `claim_id` уезжают
в query-строку, а не в тело POST-запроса.

## 10. Точка `return` и статусы

Док, `PointType`: `source`, `destination`, `return` — и про `return` сказано «добавляется
автоматически и по умолчанию совпадает с точкой отправления». Провод (2026-08-12) показал ровно это:
на два отправленных пункта в ответе приходит три. **Сегодня это документировано** — справочник тут
лучше той HTML-справки, по которой мы писали спеку в июле 2025-го.

`ClaimStatus` в справочнике — 26 значений. У нас в документе 27: лишнее — `pay_waiting`, которого в
сегодняшнем справочнике нет. Ещё в нашем `TaxiClass` стоит `sdd_long` с комментарием «здесь быть не
должно».

## 11. Источник предупреждения — открытая строка у вендора и закрытый enum у нас

Док, сущность `ClaimWarningSourceApi`: **`Type: string`**, в описании перечислены прозой два значения
(`client_requirements`, `route_points`). Никакого `Enum` там нет.

Провод (2026-08-17): пришло третье — `taxi_requirements`, которого в описании нет и сегодня. Имя
совпадает с названием секции запроса (`taxi_requirements` — поле в теле `claims/create`), то есть
словарь растёт вместе со схемой запроса и закрытым не был никогда.

Наш документ моделировал это поле закрытым перечислением — и весь ответ `claims/info` перестал
декодироваться (TD-19). Ошибка наша, вендор её не обещал.

## 12. Доступ, тестовый контур, поддержка

Док, `quickstart.md`: логин и пароль «полученные от менеджера Яндекс Доставки»; токен берётся в
личном кабинете; «OAuth-токен действует неограниченное время». Дважды на странице — «В случае
проблем обратитесь к менеджеру Яндекс Доставки».

Хост в документации ровно один: `https://b2b.taxi.yandex.net`. Песочницы нет. Тестовый **кабинет**
существует, но только как срочный: в `errors.md` есть `required_tariffs_disabled_for_user` —
«Закончился срок тестового кабинета».

Вся страница «Технические детали интеграции» — одно предложение про TLS 1.2 и шифры PCI DSS v4.

Наш собственный ранний черновик (июль 2025, `YandexDostavka/Archive/express-delivery_corrected.yaml`)
объявлял второй сервер `https://b2b.taxi.tst.yandex.net/...` с описанием `Sandbox`. Ни в
документации, ни в Postman-коллекции реальных запросов такого хоста нет. Пример того, как документ,
который ты пишешь за вендора, обрастает выдумкой.

## 14. Найдено попутно: сайт собирается не тем, чем кажется

Не про Яндекс, но про этот репозиторий — обнаружено при подготовке публикации, 2026-08-24.

`Gemfile` и `_config.yml` подключают **jekyll-polyglot**, а деплой идёт через
`actions/jekyll-build-pages@v1`, который запускает Jekyll в safe-режиме со списком разрешённых
плагинов GitHub Pages. Polyglot в этот список не входит и в продакшене **не загружается вовсе**.

Последствия, проверенные на живом сайте:

- боевые адреса несут языковой суффикс в слаге: `/articles/2025/06/03/openapi-source-of-truth.ru/`
  и `…-truth.en/` (оба отдают 200), а раздела `/articles/en/` не существует (404);
- обе перекрёстные ссылки «Read in English» / «Читать оригинал» в прошлой статье вели на
  `/2025/06/03/openapi-source-of-truth/` и `/en/2025/06/03/openapi-source-of-truth/` — **оба 404**.
  Ссылки были написаны в расчёте на polyglot, которого там нет;
- локальная сборка `bundle exec jekyll build` polyglot подхватывает (он в группе `:jekyll_plugins`
  и требуется автоматически), поэтому локально видно `/en/…`, а в проде — нет. Локальная сборка
  расходится с боевой.

**Что сделано сейчас:** ссылки в обеих статьях исправлены на адреса, которые сайт действительно
отдаёт; новые посты получили ту же схему адресов, что уже опубликована. Проверено сборкой с
Gemfile без polyglot (то есть так, как собирает GitHub Pages) — генерируются ровно четыре страницы
постов, и все внутренние ссылки в собранном сайте резолвятся.

**Что стоит решить отдельно** (это решение о сайте, а не о статье):

1. **Убрать polyglot** из `Gemfile` и `_config.yml`. Тогда локальная сборка совпадёт с боевой, а
   адреса останутся ровно теми, что опубликованы. Самый дешёвый вариант, ничего не ломает.
2. **Или включить polyglot по-настоящему** — заменить в workflow `actions/jekyll-build-pages` на
   `bundle exec jekyll build`. Тогда появятся честные `/en/…` без суффиксов в слаге, но **все
   существующие адреса изменятся**, а редиректов на GitHub Pages нет.

Ещё: `_includes/lang-switcher.html` не подключён ни из одного шаблона — мёртвый код. Не трогал.
